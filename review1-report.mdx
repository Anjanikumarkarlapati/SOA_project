# Part I — The project and how it works

## The system at a glance

AgriTech Sensing Solutions is a precision-agriculture control platform. A fleet of field sensors reports
soil moisture, soil temperature, pH and battery level. The platform scores each field's crop health
against that crop's optimal envelope, and drives irrigation valves from the score — opening zones when
moisture is forecast to fall below the optimal floor, and shutting them off early when moisture reaches
the optimal ceiling so it does not waste water.

It is a **Spring Cloud microservices system**: seven Maven modules under one reactor build, four
business services behind a reactive API gateway, a Netflix Eureka registry for service discovery, and a
browser dashboard that talks only to the gateway.

| Module | Port | Owns | Responsibility |
| --- | --- | --- | --- |
| `eureka-server` | 8761 | — | Service registry; 30 s heartbeat, 90 s eviction |
| `api-gateway` | 8080 | no data | Single entry point: JWT validation, identity headers, routing, rate limiting, CORS |
| `auth-service` | 8081 | `User` | Login, registration, 24 h JWTs, refresh tokens, revocation list, Google/Supabase federation |
| `sensor-service` | 8082 | `SensorDevice`, `TelemetryReading` | Device registry, telemetry ingestion and validation, historical queries |
| `crop-service` | 8083 | `Crop`, `HealthSnapshot` | Health scoring, optimal-range evaluation, recommendations, irrigation forecast |
| `irrigation-service` | 8084 | `IrrigationSchedule`, `Valve`, `IrrigationEvent` | Schedules, valve control, moisture cut-out, emergency stop |
| `common` | — | no data | Shared error envelope, global exception handler, caller-identity helpers |
| `web` | 3000 | no data | Next.js 16 dashboard (current) |
| `frontend` | 5173 | no data | Vite dashboard (legacy, kept for side-by-side comparison) |

Build stack, straight from the root `pom.xml` and module POMs:

| Concern | Choice |
| --- | --- |
| Language | Java 21 |
| Framework | Spring Boot 3.3.4 |
| Cloud | Spring Cloud 2023.0.3 |
| Gateway | Spring Cloud Gateway (reactive / WebFlux) |
| Discovery | Netflix Eureka client + server |
| JWT | `jjwt` 0.11.5, HMAC-SHA256 |
| Password hashing | `BCryptPasswordEncoder` (`spring-security-crypto`) |
| Persistence | H2 in-memory per service, `ddl-auto: update` |
| Frontend | Next.js 16 App Router, React 19, Tailwind v4, shadcn, Recharts |

<Callout type="note" title="One sentence that describes the whole architecture">
Every request enters through one gateway that is the only component in the system holding the signing
key; the gateway turns a token into trusted headers, and four services that each own their own data
collaborate through a registry rather than through each other's hostnames.
</Callout>

This is the diagram to have on screen when the examiner asks "walk me through what happens when a
farmer opens the dashboard".

<Mermaid caption="A single authenticated dashboard request, from click to JSON">{`

    participant G as api-gateway :8080
    participant E as Eureka :8761

    Note over B: login already done; JWT held in localStorage

    G->>G: RateLimitFilter (order -50) — 1000/min per user

    G->>E: resolve lb://crop-service
    E-->>G: healthy instance list
    G->>C: GET /api/crops + identity headers
    C->>E: resolve http://sensor-service
    C->>S: GET /api/telemetry/field/{fieldId}/latest
    S-->>C: averaged soil moisture / temp / pH
    C->>C: score against Crop optimal bands (50/30/20 weights)
    C-->>G: HealthSnapshot list
    G-->>B: 200 JSON  (or one shared error envelope)
`}</Mermaid>

Five things worth saying out loud about this flow, because each one maps to a rubric row:

1. **The browser never learns a service hostname.** `next.config.ts` rewrites `/api/*` to the gateway,
   so the origin is single and there is no CORS preflight in the happy path.
2. **The gateway is the only JWT parser in the system.** Documented verbatim in
   `api-gateway/src/main/java/com/agritech/gateway/JwtAuthFilter.java:24-28`.
3. **Discovery is used twice in one request** — gateway to service, then crop-service to sensor-service.
   Both go through Eureka service-ids, not ports.
4. **Filters are ordered deliberately**: `JwtAuthFilter` at `-100` runs before `RateLimitFilter` at
   `-50`, so the rate limiter can distinguish an authenticated user quota from an anonymous IP quota.
5. **Failures look the same everywhere.** One envelope, produced by
   `common/ApiExceptionHandler.java`, per the PRD's error contract.

## The automation logic (what makes it more than CRUD)

This is the part that separates a "microservices demo" from a "system", so it belongs in the report even
though no rubric row names it directly.

**Health score.** For each of soil moisture, soil temperature and pH: 100 inside the crop's optimal band,
losing points in proportion to how far outside it the reading sits, measured in *band widths* rather than
raw units. The three are weighted 50 / 30 / 20 toward moisture. A drift of up to 35 % of a band width is
a warning; beyond that is critical. Implemented in `crop-service/.../HealthScore.java`, covered by
`HealthScoreTest`.

**Irrigation forecast.** The moisture slope over the last six hours is extrapolated forward to the moment
it would cross below the optimal floor. Only forecasts inside a 48-hour horizon are reported — beyond
that, linear extrapolation of a noisy signal is not worth showing the farmer.

**Water saving.** Every schedule defaults to `skipIfMoist`. Before opening, irrigation-service asks
crop-service for the field's health and *skips the run* if moisture is already at or above the optimal
ceiling. A zone already running shuts itself off mid-run when it reaches that ceiling. This is the
closed loop, and it is the strongest answer to "why does this need to be more than one service?".

**Demo closure.** `sensor-service/DeviceSimulator.java` seeds 13 devices across 4 fields, backfills 48
hours of 15-minute samples on a sine daily cycle, then emits every 30 seconds. One device is deliberately
left offline and one field starts dry, so the alert paths are visible without waiting for a failure.
When a valve opens, irrigation-service calls
`POST /api/telemetry/field/{id}/irrigation-event`, and simulated moisture climbs ~1.4 per tick while
watering — so the score visibly recovers on screen. Set `SIMULATOR_ENABLED=false` to run against real
devices; they post to the same `POST /api/telemetry/ingest` contract.

## Running and demonstrating it

```powershell
./scripts/stack.ps1 start          # builds all modules, then launches in dependency order
npm install --prefix web
npm run dev   --prefix web         # http://localhost:3000
```

`stack.ps1` loads the git-ignored root `.env` into the child process environment, then starts
eureka(8761) → auth(8081) → sensor(8082) → crop(8083) → irrigation(8084) → gateway(8080) as
`java -jar <module>/target/<name>-1.0.0.jar`, blocking on each service's `/actuator/health` returning
`UP` (90 s timeout) and writing logs to `.run/`. `-SkipBuild` skips `mvnw install -DskipTests` — which
means **backend edits silently run as stale JARs unless you reinstall first**.

| Credential | Role | Sees |
| --- | --- | --- |
| `admin@agritech.io` / `admin1234` | ADMIN | Full sensor, schedule and valve control |
| `farmer@agritech.io` / `farmer1234` | FARMER | Read-only telemetry and crop health |

The dashboard never asks which role you are; navigation and controls are filtered from the `role` claim
inside the issued token. That is a good line to say in a viva — it means authorisation is driven by the
token, not by a UI setting.

Verification, both levels:

```bash
./mvnw test                  # 3 unit test classes
bash scripts/smoke-test.sh   # end-to-end against a running stack
```

The smoke test covers the PRD's section 9.3 scenarios: unauthenticated rejection, login for both roles,
forged-token rejection, the farmer/admin authorisation split, device registration, telemetry ingestion
including out-of-range rejection, health scoring from live telemetry, cross-service trend retrieval
through Eureka, manual valve control, emergency stop, schedule CRUD, and logout revocation taking effect
at the gateway. **Run this live in the review.** It is the only artifact that proves all four rubric rows
at once.

Give the services ~30 seconds after startup before the first cross-service call — that is Eureka's
registry-fetch interval, and until it completes the gateway has no route targets. Know this before the
demo, because a 502 in the first few seconds is expected behaviour and not a bug.

## Rubric 2 — Microservice Identification and Service Discovery

**The ladder.** 0 not identified · 2 few services defined · 5 basic service split · 7 well-structured
services · 10 highly modular design.

### What "highly modular" is actually testing

Three questions decide this row: *why do these boundaries exist*, *does each service own its data*, and
*can one service change or scale without touching the others*. If your decomposition story is "the
tutorial had these folders", you are at 5. If it is "each boundary is a business capability with its own
data and its own scaling profile", you are at 10.

### What your project does — the decomposition story

You have **four business services plus three infrastructure/shared modules**, and the boundaries are
defensible because each one is drawn on a different axis:

| Service | Business capability | Owns | Scaling driver | Change cadence |
| --- | --- | --- | --- | --- |
| `auth-service` | Identity and access | `User` | login bursts, negligible per-request cost | low — security code should be boring |
| `sensor-service` | Device telemetry | `SensorDevice`, `TelemetryReading` | **write volume** — scales with device count | low |
| `crop-service` | Agronomic analysis | `Crop`, `HealthSnapshot` | **CPU** — scoring and forecasting | high — the model changes often |
| `irrigation-service` | Actuation | `IrrigationSchedule`, `Valve`, `IrrigationEvent` | low volume, but **safety-critical** | medium |

Say this in the room: *the split is not by screen, it is by scaling profile and by blast radius.*
Sensor-service needs to scale with 10,000 devices writing; crop-service needs CPU for analysis;
irrigation-service needs neither, but it is the only service that can physically waste water or stress a
crop, so it is isolated so that a bad crop-service deploy cannot reach a valve. That is a modular design
argument, not a folder-layout argument.

**Data ownership is real.** Each service has its own H2 datasource and its own entities. There is no
shared database and no cross-service foreign key. When crop-service needs soil moisture it calls
`GET /api/telemetry/field/{id}/latest` — it does not read the sensor table. This is the single most
important modularity claim you have; most submissions fail it by sharing one schema.

### Service discovery — the actual mechanics

This is where you can clearly out-score the cohort, because you can show the config rather than describe
the concept.

**Server.** `@EnableEurekaServer` on port 8761 (`eureka-server`).

**Clients.** Every service carries `spring-cloud-starter-netflix-eureka-client` and registers via
config — no `@EnableDiscoveryClient` annotation is needed on the Spring Cloud 2023 line, and the
dependency plus these keys do the work:

```yaml
eureka:
  client:
    service-url:
      defaultZone: ${EUREKA_URL:http://localhost:8761/eureka}
  instance:
    prefer-ip-address: true
```

`prefer-ip-address: true` matters: it makes the registry hand back an IP rather than a reverse-DNS
hostname, which is what lets the stack run on a laptop without a DNS server.

**Consumers use logical names, never hostnames.** Gateway routes resolve through the registry:

```yaml
- id: sensor-service
  uri: lb://sensor-service
  predicates:
    - Path=/api/sensors/**,/api/telemetry/**
```

Inter-service clients do the same with a `@LoadBalanced` template — `SensorClient.java:25` calls
`http://sensor-service/...`, `FarmClient.java:29,41` call `http://crop-service/...` and
`http://sensor-service/...`. **There is not a single hardcoded `localhost:808x` in any route or client in
the codebase.** Say that sentence out loud; a lot of submissions claim service discovery and then route
to fixed ports.

**Load balancing.** `lb://` URIs are round-robined across healthy instances, which is the PRD 8.2
requirement. This is demonstrable: start a second `sensor-service` on another port, watch both appear
under the Eureka UI at `:8761`, and show the gateway alternating between them.

**Registry timings to quote:** 30 s heartbeat, 90 s eviction, 30 s client registry fetch. The last one is
the reason a fresh stack returns 502 for the first ~30 seconds — quote it as a *known trade-off of AP
eventual consistency in Eureka* rather than as a bug. That reframing alone signals real understanding.

<Callout type="note" title="The theory sentence that lifts this row">
Eureka is an AP system in CAP terms: it prefers availability and partition tolerance over a strongly
consistent registry view. That is the correct choice for service discovery, because routing to an
instance that just died is recoverable with a retry, whereas refusing to route at all is not. The 30 s
registry-fetch interval is the visible price of that choice.
</Callout>

## Rubric 3 — JWT Authentication

**The ladder.** 0 not implemented · 2 partial setup · 5 basic authentication · 7 secure implementation ·
10 robust and secure.

### What "robust and secure" is actually testing

7 means the token works and is verified. 10 means the *lifecycle* is handled — issuance, expiry, refresh,
revocation, role propagation, key management, and the attack surface — and that you can name the threats
you defended against. Expect to be pushed on: replay, forged roles, token leakage, algorithm confusion,
and what happens between logout and the next poll.

### What your project does

**Issuance.** `auth-service` verifies credentials with `UserRepository.findByEmail` plus
`BCryptPasswordEncoder.matches`, then mints a signed token:

```java
// auth-service/.../JwtService.issue()  — FR-1
Jwts.builder()
    .setId(UUID.randomUUID().toString())   // jti — the revocation handle
    .setSubject(user.getEmail())           // sub
    .claim("role", user.getRole())
    .claim("farmId", user.getFarmId())
    .claim("name", user.getDisplayName())
    .setIssuedAt(now)
    .setExpiration(new Date(now.getTime() + accessTtlMs))
    .signWith(key, SignatureAlgorithm.HS256)
    .compact();
```

| Claim | Value | Why it is there |
| --- | --- | --- |
| `jti` | random UUID | Lets a stateless token be individually revoked |
| `sub` | email | Stable user identity |
| `role` | ADMIN / FARMER | Drives authorisation without a DB round-trip |
| `farmId` | e.g. `FARM-001` | Tenant scoping |
| `name` | display name | UI only |
| `iat` / `exp` | issued / expiry | 24 h TTL, configurable via `access-ttl-hours` |

**Validation happens in exactly one place.** `JwtAuthFilter` is a `GlobalFilter` at order `-100`. It
short-circuits `OPTIONS` and a small explicit public-path list, parses the bearer token, checks the
revocation cache, and then converts identity into headers:

```java
private static final List<String> PUBLIC_PATHS = List.of(
```

<Callout type="tip" title="The detail that proves you understand the design">
The order of those two operations is the whole security model. Client-supplied `X-User-*` headers are
removed **before** the verified values are written. Without that line, any caller could send
`X-User-Role: ADMIN` and be trusted by every downstream service. Lead with this when asked how roles are
propagated — it is the difference between "we used JWTs" and "we understood the trust boundary".
</Callout>

**Authorisation.** Downstream, `common/CallerContext.requireAdmin()` throws a 403 `ApiException` unless
`X-User-Role` is `ADMIN`. Missing role defaults to `FARMER` — fail-closed to the *lower* privilege, which
is the correct default and worth stating explicitly.

**Refresh and revocation.** Access token 24 h; refresh token is an opaque UUID held in an in-memory
`TokenStore` with a 30-day TTL, exchanged at `POST /api/auth/refresh`. `POST /api/auth/logout` revokes
both the access token's `jti` and the refresh token. The gateway learns about revocations by polling
`lb://auth-service` `/api/auth/revoked` every 15 s (`RevocationCache`, `agritech.jwt.revocation-poll-ms`).

**Federated Google login.** A genuinely non-textbook addition, and it is the strongest "robust" evidence
you have. The frontend performs OAuth through `supabase-js`; the resulting Supabase token is posted to
`POST /api/auth/google`; `SupabaseVerifier` **introspects** it by calling
`{SUPABASE_URL}/auth/v1/user` rather than verifying it locally; first-time users are auto-provisioned as
FARMER on `FARM-001`; and the platform then issues its *own* internal JWT, so the rest of the system is
completely unaware that Google was involved.

That last point is the answer to "why not just use the Supabase token everywhere?". Internal tokens carry
`role` and `farmId`, keep the gateway's verification path single and fast, and let you swap identity
providers without touching four services. This is standard identity-brokering and it is worth naming as
such.

<Callout type="warning" title="There is a real technical reason behind the introspection — use it">
An earlier version of `SupabaseVerifier` verified Supabase tokens locally with the legacy HS256 JWT
secret (the `.bak` files at the repo root still hold it). Supabase moved to ES256/JWKS-signed tokens, so
local HS256 verification began returning 401. Introspecting `GET /auth/v1/user` works regardless of the
signing algorithm. Present this as a *discovered constraint and a deliberate design response* — it is one
of the few genuinely production-shaped lessons in the project, and it makes the "robust" claim concrete
rather than borrowed.
</Callout>

**Tested.** `auth-service/src/test/java/.../SupabaseVerifierTest.java` runs 7 tests against an embedded
`HttpServer` — real tests, no network, no mocks of the thing under test.

### What your project does

**Route table.** Four routes, all discovery-resolved, in `api-gateway/src/main/resources/application.yml`:

| id | uri | predicates |
| --- | --- | --- |
| `auth-service` | `lb://auth-service` | `Path=/api/auth/**` |
| `sensor-service` | `lb://sensor-service` | `Path=/api/sensors/**,/api/telemetry/**` |
| `crop-service` | `lb://crop-service` | `Path=/api/crops/**` |
| `irrigation-service` | `lb://irrigation-service` | `Path=/api/irrigation/**,/api/valves/**` |

Two deliberate choices worth explaining:

- **`spring.cloud.gateway.discovery.locator.enabled: false`.** Auto-discovery would publish every
  registered service under a `/servicename/**` path, exposing internal services to the internet through
  the gateway. Explicit routes act as an allow-list. This is a security decision, and saying so converts
  a config line into a rubric mark.
- **No `StripPrefix`.** The gateway forwards the path unchanged, and downstream controllers map the full
  `/api/...` path. This keeps the external and internal contract identical, so a service log line matches
  what the browser sent. Many projects add `StripPrefix=1` and then have divergent paths in logs; your
  choice is defensible either way — the point is that you can justify it.

**Filter chain, in execution order.**

| Order | Component | Responsibility |
| --- | --- | --- |
| `-100` | `JwtAuthFilter` | Verify HS256, check revocation, strip and set identity headers |
| `-50` | `RateLimitFilter` | Three-tier fixed-window limiting, emits `X-RateLimit-*` |
| background | `RevocationCache` | Polls `lb://auth-service` `/api/auth/revoked` every 15 s |
| shared | `GatewayResponses` | One error envelope for gateway- and service-originated failures |

Auth running *before* rate limiting is what allows the limiter to key on the authenticated user rather
than only on IP. That ordering is a design decision, not an accident.

**Rate limiting, per PRD 7.2.**

| Caller | Key | Limit |
| --- | --- | --- |
| Anonymous | client IP | 100 / min |
| Authenticated | user | 1000 / min |
| Device | `X-Device-Id` | 100 / min |

**CORS** is terminated at the gateway for `http://localhost:*` and `http://127.0.0.1:*` across all
methods, exposing `X-RateLimit-Limit` and `X-RateLimit-Remaining`. In the normal path the browser never
sees a preflight, because `next.config.ts` rewrites `/api/*` to the gateway and keeps a single origin —
gateway CORS is the fallback for the legacy Vite app on 5173.

**Observability.** `management.endpoints.web.exposure.include: health,info,gateway` — the `/actuator/gateway/routes`
endpoint dumps the live route table, and `logging.level.AUDIT: INFO` gives a named audit logger that
records rejections (`audit.warn("auth REJECTED path={} reason={}", ...)` in `JwtAuthFilter:72`).

**Health-gated startup.** `stack.ps1` blocks on each service's `/actuator/health` returning `UP` before
launching the next, so the gateway never starts against an empty registry.

## Viva questions you should expect, with the answers

**Why five services and not one?** Because the scaling axes differ — sensor-service scales with device
write volume, crop-service scales with CPU for analysis, irrigation-service scales with neither but is
safety-critical and must be isolated. And because the agronomic model changes far more often than the
device contract.

**Why Eureka and not Consul or Kubernetes Services?** Eureka is client-side load balancing with a
locally cached registry, so it survives the registry dying — an AP trade-off that suits discovery. It is
also the reference implementation for the Spring Cloud stack in use.

**Where is the signing key held?** Only the gateway and auth-service have it, and that is deliberate:
auth mints, gateway verifies, and the four business services never parse a token at all. The weakness is
that HS256 means both can mint; moving to RS256 lets the gateway hold only a public key.

**How does a downstream service know the role is genuine?** The gateway strips client `X-User-*` headers
before writing verified ones, and services are meant to be reachable only through the gateway. The
honest gap is that nothing currently *enforces* that network boundary — that is the answer to "so could
you bypass it?", and it is better given proactively than found.

**What happens if sensor-service is down when crop-service needs data?** Right now: a 2–4 second timeout
and a caught exception, degrading to whatever the response contract allows. The planned fix is a
resilience4j circuit breaker with a cached last-known-good snapshot. Naming the current behaviour
accurately, then the fix, is a full-marks answer; claiming it is already resilient is not.

**Why does the first request after startup fail?** Eureka clients fetch the registry every 30 seconds, so
for roughly 30 seconds the gateway has no route targets. That is the visible cost of AP eventual
consistency in the registry, and it is why `stack.ps1` health-gates startup.

**Why does the gateway poll auth-service instead of sharing its database?** Because sharing a database
across services would break the data-ownership boundary that makes the decomposition valid in the first
place. A read-only polled endpoint keeps the boundary at the cost of a 15-second staleness window; Redis
removes the window without removing the boundary.

**What is `skipIfMoist` and why does it need two services?** It is the water-saving rule: do not irrigate
a field already at the optimal ceiling. The *knowledge* of optimal ceilings and current health belongs to
crop-service; the *authority* to open a valve belongs to irrigation-service. Separating knowledge from
actuation is precisely why the boundary exists.
